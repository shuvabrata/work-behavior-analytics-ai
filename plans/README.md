## Findings considered and rejected

- **Dedicated seeded Keycloak users for the test suites (plan 004).** Rejected
  there; plan 005 revisits the neighbouring question and rejects it again:
  `skipped`-versus-`failed` for the seven `unit` modules requires either a
  literal in code or a repository variable, and a repository variable was
  chosen so no username is ever committed.
- **A default username inside `tests.auth_helpers.realm_username` (plan 005).**
  Rejected: a default is the hardcoded username the plan exists to remove, and
  it would silently run the suite against an account that is not the one the
  stack seeded.
- **Rewriting the `dev-admin` / `dev-user` mentions in DONE plans 001, 002, 004
  and `docs/project-plan/` (plan 005).** Rejected: those are historical records of
  what was verified at a past date; rewriting them makes the record claim a name
  that did not exist then.
- **Leaving the forced-change behaviour to `temporary: true` alone (plan 006).**
  Rejected: measured to be a no-op on Keycloak's realm-import path. The admin-API
  path honours it, which is why a probe that only exercised that path would have
  wrongly cleared it.
- **Parameterise `common/auth/service_token.py` for the admin client.** Rejected:
  it is connector-runtime code that reads `os.environ`; the API has a settings
  object and a separate secret, so a local cache in `app/auth/keycloak_admin.py`
  is cheaper and touches nothing the connector images ship.
- **Move existing admin routes under `/api/v1/admin/`.** Rejected for this plan:
  pure churn across every UI call site, no functional gain; `AUTHZ_MATRIX`
  already declares the grant level per route.
- **Role filtering in the user list.** Rejected: Keycloak's `/users` endpoint
  cannot filter by role; doing it correctly needs a different endpoint and a
  design of its own.
- **Integration tests that create/update/delete real Keycloak users.** Rejected:
  the operator verifies those by hand (Step 14); the unit suite covers the
  guards against stubs.
- **Dual-name acceptance during the role rename (plan 002).** Rejected: the
  re-seed destroys every Keycloak session and refresh token anyway, so a
  transition window would add a second code path and a later cleanup commit
  while protecting nothing.
- **A shared roles constant module (plan 002).** Rejected: `_MAPPED_ROLES`
  (auth allowlist) and `ASSIGNABLE_REALM_ROLES` (assignable subset) are already
  the named homes; this rename changes their contents, not their structure, so a
  new module would be a refactor riding a rename.
- **An Alembic data migration rewriting `auth_session.roles` (plan 002).**
  Rejected: the column is a write-only snapshot never read for authorization
  (`Principal` is always rebuilt from the token), and the re-seed invalidates
  every session it describes, so the rows are truncated instead.
