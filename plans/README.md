**Two orderings are load-bearing and must not be "optimised":**

- **055 before 056/057.** A bearer-only API breaks the producers and consumer
  the moment enforcement switches on, and command-status reporting does not
  degrade gracefully.
- **056 before 057.** The UI must be able to *send* a bearer before the API
  starts *requiring* one, or every page dies on its first API call. Between 056
  and 057 the app works with real logins but the API still accepts
  unauthenticated requests — a deliberate, short window that 057 closes.

  Verified against the live tree at planning time: `pytest -m unit tests -q` →

  rather than edited per handler); `src/ui/layout.py:27-28` sets both Dash

  at `/app/stream/<id>`; `tests/test_chat_stream_bridge.py:171-176` is **vacuous**

  Dockerfile change.

  **Decisions that override the design doc** (the doc is corrected by plan 061):
  `wba-service` is exactly four endpoints, not the eleven the endpoint matrix
  marks; `/settings/runtime-snapshot` is user+admin+service, not service-only;
  theme writes stay admin-only until Plan D; revocation of an already-issued
  bearer is bounded at 15 minutes, not immediate; and `/api/v1/auth/token` plus

  "bearer only".

  **The design doc's "one public URL" open item was wrong** and is corrected in
  the plans: a container's `localhost` is itself, so the API needs a second
  setting (`KEYCLOAK_INTERNAL_URL`) for discovery/JWKS/token, with

- **045**: Finding still present and reproduced on `40ef1e5`.
  `validate_read_only_query()` (`src/app/api/graph/v1/query.py:38`) uppercases
  the whole query (`:60`) and regex-matches `WRITE_KEYWORDS` (`:31-35`) with
  `\b` boundaries (`:63-74`), so it also matches inside string literals.
  `-` is a non-word character, so an id like
  `github::Repository::facebook/create-react-app` matches `\bCREATE\b` and the
  read-only query is rejected as a write. Verified directly:
  `validate_read_only_query("MATCH (a:Repository {id: 'github::Repository::facebook/create-react-app'})-[r]-(b) RETURN a LIMIT 50")`
  → `False`; the same query with `acme/foo` → `True`.

  ("P1 once any surface auto-executes a user-supplied id") is now met: 044 landed
  as **PR #340** (`a2ab3dd`), so the Activity Timeline card builds its deep link
  through `graph_deep_link` (`pages/timeline/helpers.py:664`, called from
  `pages/timeline/callbacks.py:1270`) and the Graph page auto-executes it
  (`graph/callbacks/right_panel.py:104` → `graph/callbacks/query.py:189`). The
  plan's "Affected surfaces" table said this path "cannot fail" today — that
  statement is now false and has been corrected in the plan file. The two
  `search.py` call sites (`:348`, `:457`) remain pre-existing exposure.

  **Still a problem statement, not a plan.** The five open questions in the file
  are unresolved; the central one is whether to make the validator literal-aware
