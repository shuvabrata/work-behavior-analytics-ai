- **052**: Planned at `5210f00` on 2026-10-28. Not an audit finding — it is
  Plan B of the AuthN/AuthZ programme. Written from a structured interview with
  the operator; the 18 decisions taken are recorded in the plan's own
  "Decisions taken during planning" table, so they are decisions rather than
  omissions.

  Verified at planning time, against the live tree and a **running, populated
  stack**: the Dash layer already imports no database driver (grep across
  `dash_app/` for `sqlalchemy`/`neo4j`/`asyncpg`/`app.db`/`alembic` → no
  matches), so the isolation is real but unenforced; 35 files (~20,800 LOC) under
  `dash_app/` import outside `app.dash_app`; there are exactly **56** `requests.*`
  call sites across 13 files; **12** module-level constants freeze runtime
  settings at import; and `src/app/api/graph_themes/v1/service.py:28` is the only
  real API→UI import (`get_theme_tokens`).

  **Three findings that shaped the plan, none of them in the design doc:**
  1. The 12 module-level constants are a **verified pre-existing bug** — after a
     cache refresh, `chat.TIMEOUT_SECONDS` still returns the import-time value.
     Step 7 fixes it with a test that must fail on the old pattern.
  2. `pages/connectors/layout.py:966-978` reads a GitHub PAT from the UI
     process's environment. The token is *not* displayed (`_mask_secret_ui`
     returns a fixed string), but keeping the page working would require passing
     the secret into the UI container. `GET /api/v1/settings/` already returns
     `is_configured`, so the page needs no secret. Step 8.
  3. `search_in_graph` is **not** equivalent to `/search` — verified live:
     unscoped `/search?q=review` returns 20 of 22 under `page_size`, while the
     canvas has 223 nodes. A literal swap would silently stop highlighting
     nodes. Step 10 adds an optional `ids` param instead.

  Two of the design doc's figures are **understated** and the plan uses the
  measured ones: it says 30 files / ~19,000 LOC import outside `dash_app/`
  (measured 35 / ~20,800), and 92 test files reference `app.dash_app` (measured
  **43**, plus 11 for `app.main`, 11 for `ASGITransport`, 2 for `TestClient`).
  The `app.main` count matches exactly.

  **Requires a running Compose stack** — Steps 9, 10, 12, 13, 16 and 18 all
  depend on it, and Steps 9/10 compare against real data (223 people, 4818
  pairs, 5041 elements; the collab response is 1.67 MB). The stack was up and
  healthy at planning time. Note that `curl -k` is blocked by the sandbox
  classifier in some harnesses; the plan's commands use strict TLS, which works
  on any machine that ran `mkcert -install` (Plan 051's Gate 7 established this).

- **005**: Finding still present. `_run_sync` in
  `src/app/ai_agent/mcp_integration/client_manager.py` spawns a daemon worker
  thread and joins it with no timeout — `worker.start()` at `:52`,
  `result_queue.get()` at `:53`, `worker.join()` at `:54`. If the MCP server
  hangs, the calling thread blocks indefinitely; the `request_timeout_seconds`
  (default 20, `:33`) applies only to the HTTP client inside the worker, not to
  the join. The file has drifted since the plan's `ec14dc5` stamp (117 insertions
  / 9 deletions — a `_with_session` debug log, a `# type: ignore` in
  `_serialize_content_item`, and a new `_run_list_tools_test` method), but
  `_run_sync`'s body is byte-identical to the plan's excerpt, so the steps are
  unaffected. `Planned at` has been refreshed to `40ef1e5`.

- **045**: Finding still present and reproduced on `40ef1e5`.
  `validate_read_only_query()` (`src/app/api/graph/v1/query.py:38`) uppercases
  the whole query (`:60`) and regex-matches `WRITE_KEYWORDS` (`:31-35`) with
  `\b` boundaries (`:63-74`), so it also matches inside string literals.
  `-` is a non-word character, so an id like
  `github::Repository::facebook/create-react-app` matches `\bCREATE\b` and the
  read-only query is rejected as a write. Verified directly:
  `validate_read_only_query("MATCH (a:Repository {id: 'github::Repository::facebook/create-react-app'})-[r]-(b) RETURN a LIMIT 50")`
  → `False`; the same query with `acme/foo` → `True`.

  **Priority raised P2 → P1 this reconcile.** The plan's own promotion condition
  ("P1 once any surface auto-executes a user-supplied id") is now met: 044 landed
  as **PR #340** (`a2ab3dd`), so the Activity Timeline card builds its deep link
  through `graph_deep_link` (`pages/timeline/helpers.py:664`, called from
  `pages/timeline/callbacks.py:1270`) and the Graph page auto-executes it
  (`graph/callbacks/right_panel.py:104` → `graph/callbacks/query.py:189`). The
  plan's "Affected surfaces" table said this path "cannot fail" today — that
  statement is now false and has been corrected in the plan file. The two
  `search.py` call sites (`:348`, `:457`) remain pre-existing exposure.

  **Still a problem statement, not a plan.** The five open questions in the file
  are unresolved; the central one is whether to make the validator literal-aware
  (correct, but loosens a security control that is currently a deliberate
  over-approximation) or to route around it at the deep-link call sites (no
  security change, leaves the next caller exposed). Do not hand this to an
  executor until that is decided — promote it to a real plan with `/improve plan`
  once the direction is chosen.
